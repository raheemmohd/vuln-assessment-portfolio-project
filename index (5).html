What a scan config actually looks like

# Nessus: Basic Network Scan, key settings
Scan type: Basic Network Scan
Targets: 192.168.56.0/24
Port range: default (top 4790 ports)
Credentials: SSH/SMB configured for authenticated scan → far fewer false positives

# OpenVAS via CLI (gvm-cli) — kick off a task
gvm-cli --gmp-username admin --gmp-password *** socket \
  --xml "<start_task task_id='TASK_UUID'/>"

# pulling a specific CVE's details from the National Vulnerability Database
curl -s "https://services.nvd.nist.gov/rest/json/cves/2.0?cveId=CVE-2017-0144"

Authenticated scans matter enough to call out separately: an unauthenticated scan only sees what's exposed on the network; giving the scanner valid credentials lets it check locally-installed software versions too, which is where most of the real findings actually are.

3 · Reading CVSS scores

A CVSS score isn't one number pulled from nowhere — it's built from a vector string I can actually read.

CVE-2017-0144 (EternalBlue)
CVSS 3.1 Base Score: 8.1 (High)
Vector: AV:N/AC:H/PR:N/UI:N/S:U/C:H/I:H/A:H
decoding the vector string
MetricValue hereMeaning
AV — Attack VectorNetworkExploitable remotely, over the network
AC — Attack ComplexityHighRequires some specific conditions to line up
PR — Privileges RequiredNoneNo credentials needed to attempt exploitation
UI — User InteractionNoneNo victim click or action needed
C/I/A — Confidentiality/Integrity/AvailabilityHigh/High/HighFull compromise possible across all three

PR:N and UI:N together are why a "High" (not even "Critical") CVSS score like this one still gets escalated hard in practice — no credentials and no user interaction needed means it's wormable, exactly what made EternalBlue the engine behind WannaCry.

4 · Risk prioritization model

CVSS alone isn't enough — I layer exposure and asset value on top before deciding what gets fixed first.

priority = CVSS base score × exposure × asset criticality
example prioritization inputs
FactorLowHigh
ExposureInternal-only, firewalledInternet-facing, no compensating controls
Asset criticalityTest/dev machineProduction domain controller or database

A medium-CVSS finding on an internet-facing production server routinely outranks a critical-CVSS finding on an isolated test box in my actual fix order — this is the difference between a vulnerability scanner's output and a real prioritized backlog.

5 · Case study 1 — a critical finding (MS17-010 / EternalBlue)

A scan result I traced all the way to a confirmed, exploitable SMB vulnerability.

Finding: MS17-010 — SMBv1 Remote Code Execution critical

STEP 1 — SCAN RESULT 
Nessus Plugin ID 97833
Host: 192.168.56.30
Severity: Critical
Synopsis: The remote Windows host is affected by multiple vulnerabilities in SMB
CVE: CVE-2017-0143, CVE-2017-0144, CVE-2017-0145, CVE-2017-0146, CVE-2017-0148
STEP 2 — VALIDATION

I confirmed SMBv1 was actually enabled and reachable rather than trusting the plugin result alone.

nmap --script smb-vuln-ms17-010 -p445 192.168.56.30

Host script results:
| smb-vuln-ms17-010: 
|   VULNERABLE:
|   Remote Code Execution vulnerability in Microsoft SMBv1 servers (ms17-010)
|     State: VULNERABLE

This is the same target I later gained SYSTEM access on in my Red Team Lab project — this scan is what would have flagged the exposure before anyone got that far, if I'd caught and fixed it first.

STEP 3 — SCORING & PRIORITIZATION

Using §4: CVSS base 8.1 (high, per §3), exposure high (SMB reachable, no segmentation in this lab), asset criticality high (domain-joined Windows host) → escalated to the top of the remediation backlog, ahead of several "critical"-labeled findings on lower-value hosts.

STEP 4 — REMEDIATION & VERIFICATION

Recommended fix: apply MS17-010, disable SMBv1 entirely where not required, and segment SMB traffic behind a firewall rule. I rescanned after applying the patch and confirmed the plugin no longer fired.

Nessus rescan — Plugin 97833: not triggered. Finding closed, verified.

6 · Case study 2 — a false positive, caught before the report

Just as important as finding real issues: knowing when the scanner is wrong.

Finding: "Apache HTTP Server 2.4.49 Path Traversal" (CVE-2021-41773) flagged high, downgraded

STEP 1 — SCAN RESULT

OpenVAS flagged the target's Apache instance as vulnerable to CVE-2021-41773, based on the version banner reporting 2.4.49.

STEP 2 — VALIDATION

Version-banner-only detection is exactly where false positives live, so I manually tested the actual exploit path rather than trusting the banner match.

curl -s --path-as-is "http://192.168.56.20/cgi-bin/.%2e/%2e%2e/%2e%2e/%2e%2e/etc/passwd"

404 Not Found

No traversal — checking the config directly showed Require all denied was already set on the affected paths, and the mod_cgi module that CVE-2021-41773 depends on wasn't even loaded. The scanner matched a version string; it didn't check whether the vulnerable code path was actually reachable.

STEP 3 — DISPOSITION

I downgraded this from the scanner's "critical" to "informational — not exploitable in this configuration" in the report, with the validation steps included as evidence, rather than either silently dropping it or reporting it at face value. Both of those alternatives are worse: dropping it hides a real version mismatch worth patching eventually; reporting it at face value burns the client's trust and remediation time on a non-issue.

7 · Reporting & remediation tracking

A scan report that just lists CVEs doesn't drive action — what I actually hand over looks different.

What goes in my report

  • Executive summary: risk posture in a paragraph, not a CVE list
  • Findings sorted by my priority model (§4), not raw CVSS alone
  • Validation evidence for anything above medium severity
  • A remediation owner and target date per finding

Tracking to closure

A finding isn't done when it's reported — it's done when a rescan confirms it's gone, as in case study 1. I keep a simple open/verified-closed status per finding rather than treating the report as the final deliverable.

10 · Where vuln management is heading

GROWING FAST

Continuous exposure management

Point-in-time quarterly scans are giving way to always-on scanning that catches new CVEs and new assets the same day they appear, not the next scan cycle.

MATURING

Risk-based prioritization platforms

Tools increasingly automate the §4 model — layering exploit-in-the-wild data and asset context onto raw CVSS automatically, instead of an analyst building the priority list by hand.

GROWING

Attack path validation

Beyond "is this CVE present," newer platforms simulate whether a chain of lower-severity findings actually connects into a real attack path — closer to what I did manually across my Red Team and Vuln Assessment projects.

EARLY

AI-assisted patch prioritization

Early tools are using LLMs to summarize which patches matter most given an organization's specific exposure, though validating the recommendation is still a human job.

11 · Quick glossary

CVE
Common Vulnerabilities and Exposures — a unique public identifier for a specific known vulnerability.
CVSS
Common Vulnerability Scoring System — a standardized formula that turns a vulnerability's characteristics into a 0–10 severity score.
Authenticated scan
A scan run with valid credentials on the target, allowing it to check locally installed software versions, not just network-exposed services.
False positive
A finding flagged by a scanner that doesn't hold up under manual validation.
Attack surface
Everything about a system that's reachable and could be a point of attack.
Remediation SLA
The agreed maximum time a finding of a given severity is allowed to stay open before it's considered overdue.
